Я разрабатываю PHP микро-фреймворк "Joke". 
Контекст:
1. В фреймворке пока НЕТ единого слоя абстракции для хранения данных (ни файлов, ни БД, ни кэша).
2. Стек: PHP 8.4/8.5, строгая типизация, ООП.
3. Есть Service Providers, Middleware и система конфигурации.

Задача:
Спроектируй архитектуру системы Rate Limiting, которая одновременно станет первым шагом к созданию универсального слоя хранения (Storage Layer) во фреймворке.

Требования к архитектуре:
1. Интерфейс хранилища (Storage Interface):
   - Спроектируй универсальный интерфейс `StorageInterface` (или `CacheInterface`), который позволит хранить пары ключ-значение с TTL (временем жизни).
   - Этот интерфейс должен стать основой для будущих драйверов: FileDriver, ArrayDriver (для тестов), RedisDriver.

2. Реализация "из коробки":
   - Так как внешних БД пока нет, предложи эффективную реализацию драйвера на основе файлов или SQLite (в режиме in-memory или WAL), которая будет работать быстро и безопасно в многопоточной/многпроцессной среде (учти блокировки).

3. Алгоритм Rate Limiting:
   - Выбери алгоритм (Token Bucket или Sliding Window), который лучше всего ложится на выбранное тобой простое хранилище. Объясни почему.
   - Как обеспечить атомарность операций инкремента счетчика без использования сложных транзакций БД?

4. Интеграция в Joke Framework:
   - Как зарегистрировать этот Storage и RateLimiter через Service Provider?
   - Как сделать так, чтобы настройки лимитов (например, "100 запросов в минуту") были гибкими и не требовали перезагрузки сервера?

5. Идентификация:
   - Предложи механизм определения уникального клиента (IP, User ID), который можно будет легко расширять в будущем.

   
Вся документация и phpsoc которые потребуется написать - на русском языке
   
Результат:
1. Код интерфейсов `StorageInterface` и `RateLimiterInterface`.
2. Пример реализации FileBasedStorage (с учетом конкурентного доступа).
3. Схема взаимодействия Middleware -> RateLimiter -> Storage.
4. Аргументация выбора технологии хранения для старта проекта.
